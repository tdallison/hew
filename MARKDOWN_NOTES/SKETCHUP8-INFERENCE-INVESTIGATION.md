# SketchUp 8 inference investigation

## Scope and identity

Static REA 6.8.0 / Ghidra 12.1.4 analysis of the supplied `SketchUp.exe`, PE x86, SHA-256 `81484cc68070239d3852cb2fd4e1f7722c3cd96da9bc11973ca365fd5dd178d5`. Addresses below are Ghidra virtual addresses for image base `0x400000`. The startup budget was raised to 1,800,000 ms for this REA process. Ghidra completed this import and the focused queries. The analysis is static; no native execution trace was recorded.

The referenced Evidence IDs are in [sketchup8-inference-evidence-20261103.json](sketchup8-inference-evidence-20261103.json). REA's decompilation is reconstructed pseudocode, not original source; unknown types, compiler artifacts, unresolved virtual calls, absent PDB information, and Ghidra function boundaries limit conclusions. Ghidra may also mark some allocator calls as non-returning, truncating particular decompilations. The executable was not modified.

## Observed native code

1. **Point classes.** Ghidra's string inventory contains RTTI names for `CInputPointVertex`, `CInputPointMidpoint`, `CInputPointOnEdge`, `CInputPointOnLine`, `CInputPointOnFace`, `CInputPointOnAxis`, `CInputPointIntersection`, `CInputPointConstrained`, `CInputPointFinder`, and `CInputPointManager`, among others (`ev_37d6aa65534a7f75ef40e17606a433a908eab8fca0bf5d501a2aeff6a53af507`). These identify type names, not a complete list of behavior. A search for literal `Near` found no matching input-point RTTI in the defined-string inventory (`ev_ffd220dce5c4ca3561ba46d3debcbfdce7b550bf6923b8dfa4a782c3ef63a344`); this does not prove the feature or name is absent elsewhere.
2. **Class-specific cues.** Virtual-table-associated functions return the text `Endpoint`, `Midpoint`, `On Edge`, `On Line`, `On Face`, and `Intersection`; a separate axis routine selects red/green/blue, parallel, and perpendicular labels based on an integer field. Evidence: `ev_13769ddd88d3a9663e5ca85bb8f5d24e4fc54fc00931e092ec9cf429288c4748`, `ev_fe2ae06e68374d7c5f1da118703c27a22dabda4ddf76df77ef3ed289d1c0fdbf`. These functions provide labels; they do not themselves prove candidate ranking or cue rendering.
3. **Midpoint computation.** The `CInputPointMidpoint` virtual table points to `0x552840` (`ev_5d7aac9b17909a8eab9d5c0526c854be1b7108d96f029b95356a7d28c5c898d0`). That method calls `0x95b280`, which passes two three-component records and the same 0.5 double coefficient twice to `0x7feca0`. That helper computes a component-wise weighted sum. The inferred normal result is therefore `(A+B)/2` for the two referenced records. The midpoint method can replace that initial result through a virtual call and can apply a transform when its instance-path condition is met; the exact object types and conditions remain unresolved. Evidence: `ev_e2f48731e02c663e5e63357015fad085b0f6e3844b532dc644ccd41013178632`, `ev_4981376dbd8abbabda27d5ea09e30e576752de65efe96dcea907a5823e291be3`, `ev_13769ddd88d3a9663e5ca85bb8f5d24e4fc54fc00931e092ec9cf429288c4748`, and assembly `ev_84d961eee518597dbfa9b17da09a2ae80be92df0f2822862a0bc16e5b1d229d8`, `ev_0a1efad455947e2b828f656f898c1c4964be2ad75f0521c60d4d557efae5d120`.
4. **Picking and distance.** A rectangle-related path `0x6fcab0` invokes `0x55ea70`, which calls `0x55e6f0`. The latter calls `0x5592a0` to examine a list of input-point-like objects, applies a type-dependent and a further eligibility test, and keeps the candidate with the lowest metric. The metric routes through `0x7ff2b0` and `0x7feee0`; `0x802010` computes a vector cross product and `0x7feee0` takes its magnitude (subject to a small-value check). In context this is consistent with perpendicular distance from a point to a ray when the direction is normalized. The exact coordinate space, normalization, eligibility rules, and complete selection policy are not established. Evidence: `ev_bc40e7c789cbf40de703af237c051a835663a60836987311606b30df49452daf`, `ev_4981376dbd8abbabda27d5ea09e30e576752de65efe96dcea907a5823e291be3`, `ev_58c45e5fa147090a900ac4268c663f209298809583186fc9cb8d0569251b9a46`, `ev_6247b23028f7d9d0ecf32973a13e859e68aa268eb9f20718a0f8db781031321b`, `ev_fe2ae06e68374d7c5f1da118703c27a22dabda4ddf76df77ef3ed289d1c0fdbf`, `ev_9c46cd4d746a5376a9c1ee69c8a7f972e739ed083f3e0ab966ac5ae4a0735f33`, and assembly `ev_cf975a67b04bb006451680272478ad8086de84a7e1f4ee226f73fb6b4ab6e5ef`.
5. **Intersections and staged fallback.** `0x55e140` contains a conditional sequence of candidate-producing calls. One branch invokes `0x5586d0`, which iterates pairs of records, invokes a geometric helper, checks eligibility, compares a metric, and can construct an intersection input point through `0x5552d0` -> `0x554d30` -> constructor `0x5541e0`. Another helper (`0x7f9910`) calls a two-line calculation, averages two resulting 3D points, and checks them against a tolerance. These are evidence for a staged, conditional process with geometric intersection candidates, not a complete universal priority table. Evidence: `ev_58c45e5fa147090a900ac4268c663f209298809583186fc9cb8d0569251b9a46`, `ev_6247b23028f7d9d0ecf32973a13e859e68aa268eb9f20718a0f8db781031321b`, `ev_fe2ae06e68374d7c5f1da118703c27a22dabda4ddf76df77ef3ed289d1c0fdbf`, `ev_54924dd3ac16ccc5a2f4e55c0c19331b96f45fa604fa6ea69956612b9981d2a4`, `ev_1e9a22aa1125a9d4bab3363e79412ca09044716be5ce071fb7e45e63d0d50fe1`, and `ev_5a295500777173689306fa16632b09b6f246a10f62c459a3333221b55667fbbf`.
6. **Tool connection.** `0x5a41b0` initializes a `CRectangleTool` object with a `CPointSnapper` subobject. A shared pointer-input path calls the finder routines above. `0x5a1980` initializes `CPushPullTool`; `0x5a1bb0` calls `0x5a0ba0`, which branches based on a stored object and initializes geometry-related state. These observations connect tool state to picking/geometry helpers, but do not yet recover full rectangle or extrusion algorithms. Evidence: `ev_bc40e7c789cbf40de703af237c051a835663a60836987311606b30df49452daf`, `ev_2ab7f5a238b250f9669a8adc95a83f8d742f6f1e23dad584806ae2c90612ba4b`.

## Open questions and next probes

- Determine exact eligibility, occlusion, candidate generation, and tie-breaking rules; recover the roles of the object fields and virtual calls rather than equating the observed list minimum to the entire inference engine.
- Resolve the ray construction, units and normalization, dynamic screen tolerance, and the conditions under which midpoint replacement/instance transforms occur. Probe endpoint versus midpoint versus edge when candidates overlap at different zoom levels.
- Trace the line/pencil tool's dispatch into `CInputPointFinder`; a defined-string search for `LineTool` found `selectLineTool:` and `CDivideLineTool`, but did not establish the pencil class. `CSketchTool` is a useful candidate: its constructor sets that vtable, a vtable entry returns start-point and end-point prompts, and it shares a two-point handler (`0x6fc3d0`) that calls `0x55e6f0`/`0x55ea70`. This still does not prove that Pencil dispatches to `CSketchTool`; trace the command-to-constructor path. Evidence: `ev_35730cdf0c4abaaaa003aafa668a66e8a72bf17b5663981b90e6f5b1cc3fca86`, `ev_d8beeaf3711bc45a09cd5e6d1cce02e226642ea6943a1b47d23c35e7f0b050ae`, `ev_9810fab247d585625079e328010ab3f2ed633059549375ed26ecd3eecd49c45f`, `ev_6f790f7196b20c8d0b57338e9243658c7d83cbe460e6dd4a78554b9c2f96690b`, and `ev_8f854a8f5cad6f64ccbf8f0ab600ef9bcd004a7448766c4a43fb094719ecbd53`.
- Trace Push/Pull controller and geometry mutations to recover face selection, signed distance, copy mode, and through-cut behavior. Runtime observations against SketchUp 8 are needed to validate any proposed interpretation.
- `0x559670` contains comparisons against `0.9848` and loops over three generated directions, but the semantics and normalization of those vectors are not yet proven; do not treat that literal as a snap angle or user-facing threshold without further evidence.

REA snapshots retain eligible query evidence, not a reusable full Ghidra program database. Fresh queries in a future session can require another cold import.

## Follow-up static trace, 2026-11-05

The same executable and Ghidra profile were used for this follow-up. The earlier snapshot was imported, and the resulting 69-record evidence bundle and eligible query snapshot were saved as [sketchup8-inference-evidence-20261105.json](sketchup8-inference-evidence-20261105.json) and [sketchup8-inference-snapshot-20261105.json](sketchup8-inference-snapshot-20261105.json). A fresh provider import was necessary. The first client request timed out at 450 seconds while Ghidra was still starting; a separately queued batch completed after startup. This is static analysis, not an execution trace. Ghidra lacks the matching PDB and some pseudocode contains type-propagation and function-flow warnings.

- **Eligibility and depth-related comparison:** The previously recovered `0x8f9160` invokes a virtual predicate and calls `0x8f8aa0` only when the predicate's low bit is set. The latter's conditional branch computes two three-dimensional distances with `0x7fee90`, then invokes `0x449220`, which checks whether their difference reaches a global threshold. Initialized bytes at `0xbf66f8` decode as the double `0.001`, and at `0xbf6708` as approximately `1e-20`; the latter gates very small squared distances. The global values might be changed at runtime. This is evidence of a conditional 3D distance comparison, not a proven occlusion rule, screen-space aperture, or unit conversion. Evidence: `ev_6247b23028f7d9d0ecf32973a13e859e68aa268eb9f20718a0f8db781031321b`, `ev_5a295500777173689306fa16632b09b6f246a10f62c459a3333221b55667fbbf`, `ev_c46fc724a475f57e7115b9aada1ff7aa0f020e51801c98a5956182a4e4d0afab`, and `ev_7e03f864702cdc0791e3740b247018959df23802773753b74d24e760dc5cb34b`.
- **Ray direction:** `0x434910` initializes a `CRay3d` from two three-component records; `0x8019e0` subtracts them and `0x801660` normalizes the resulting vector subject to a tiny-value check. This supports the earlier interpretation of a perpendicular point-to-ray metric in the observed path, but does not determine the entire candidate-selection policy. Evidence: `ev_c46fc724a475f57e7115b9aada1ff7aa0f020e51801c98a5956182a4e4d0afab`, `ev_c9abfc3391ff4637cb0547ab5b87545f20c564429036ce4b75266af1e78a55b9`, and `ev_b6ee1aad1e6cb0525c99907c772a13933cf8ad319b4cf69399fa100b9ab25807`.
- **Shift-related reset path:** `0x5563e0` stores the integer `3` into a field at offset `0x4a0`. A `CSketchTool`-associated routine `0x6fb8a0` tests key code `0x10` (Windows Shift), invokes that setter, clears another byte, and conditionally dispatches an update. A related pointer path `0x6fc3d0` also invokes the setter when its modifier mask lacks bit `2`, before requesting a point. This is consistent with a Shift-release/reset path, but the key-event polarity, meaning of mode `3`, stored lock direction, and complete lifecycle remain unproven. Evidence: `ev_8f854a8f5cad6f64ccbf8f0ab600ef9bcd004a7448766c4a43fb094719ecbd53` and `ev_c46fc724a475f57e7115b9aada1ff7aa0f020e51801c98a5956182a4e4d0afab`.
- **Push/Pull movement gate and mode:** In the `CPushPullTool` virtual table, `0x5a2c80` compares two incoming integer coordinate values against values stored during `0x5a1bb0` initialization; with a target present and an operation inactive, it starts an operation when either absolute difference exceeds `2`. The same coordinate pair is passed to the input-point picking path, supporting an interpretation as pointer coordinates, but physical pixels and DPI behavior have not been established. The `0x5a3020` handler toggles a byte for key code `0x11` (Windows Control) and, under an active-operation condition, resets and recreates the operation using that mode. It does not by itself prove how geometry is changed. Evidence: `ev_572f27712dfda2f87da8e6d50756ce79881f0b26d1b8608221b39d720fdd5655`, `ev_2ab7f5a238b250f9669a8adc95a83f8d742f6f1e23dad584806ae2c90612ba4b`, and `ev_c34bb657385c6aa34d6e7926c6049eb024cdd7bd07e55bab82a7da0124d01c6d`.
- **Push/Pull signed distance and limits:** `0x5a2280` combines a filtered input-point pick with a ray-based fallback. One path computes a distance from a starting point and negates it if the displacement's dot product with a stored direction is negative. The fallback passes a calculated value to `0x6f3af0`, which returns zero below the global `0.001` and otherwise rounds using a step obtained from `0x9c8920`; that step depends on other fields and a helper. `0x5a10b0` computes a delta from the previous distance, calls a limiting helper, and applies the delta only when its absolute value meets that same global threshold. An `Offset limited to` message exists on the limiting path. These observations do not establish the native distance unit, the limits' meanings, or Boolean topology. Evidence: `ev_b6ee1aad1e6cb0525c99907c772a13933cf8ad319b4cf69399fa100b9ab25807`, `ev_3e989ecd3cd26b280d9c146d70f0d90799faa53afc0cdefa053683634ae45771`, and `ev_d0cf53f762f69ee69ae88b46061be8c866960e2fba52dbfa9da15fe9ba1c08e7`.

Exact inference eligibility, occlusion, acquisition tolerance, lock-state transitions, Push/Pull unit conversion, and topology/cut behavior remain open. The observed numeric constants should not be transplanted into a meter-based reconstruction without establishing their coordinate domains and runtime settings.

Separate [runtime comparisons](SKETCHUP8-RUNTIME-COMPARISON.md) now record bounded API/UI behavior for endpoint acquisition, normal/copy cap extension, and an exact inset through-cut. Those observations inform the independent implementation and regression fixtures; they do not resolve the native controller's units or constitute an instruction-level execution trace.

## Follow-up: face construction (2026-11-06)

An extended Ghidra run produced [a separate evidence bundle](sketchup8-pushpull-evidence-20261106.json) for `FUN_007efef0` (record `ev_6afd7972938c4fdc040114725015757579d9b7f63b294e34641ddf473581c48e`). Ghidra identifies `FUN_007f0670` as a caller. The decompilation shows allocation followed by one call to `0x9711c0`, four calls to `0x9d3a80` using the resulting object, and a call to `0x965ea0` followed by `0x93f270`. This is consistent with constructing a loop, four edge uses, and a face, but those class assignments rely on the earlier investigation and are not established by this function's recovered types alone. Five indirect calls remain unresolved, so the complete control flow and role in Push/Pull are not established. This is static evidence, not an execution trace or original source code.

Reviewing the existing 2026-11-05 batch decompilation adds detail to the movement path: `0x5a10b0` passes its distance delta by reference to `0x7ee5d0`. When a field at offset `0x58` is nonzero, that helper evaluates a three-component dot product plus an offset against two stored bounds, and adjusts the requested delta when it is outside that interval. The caller then sends the adjusted value to `0x7eea80`; that function branches between `0x7ee6a0` and `0x7f3da0` based on a stored byte. These are structural observations from decompiler output, not proof of the units, physical meaning of the interval, or complete geometry effects. The record is in [the 2026-11-05 evidence bundle](sketchup8-inference-evidence-20261105.json), batch containing addresses `0x7ee5d0` and `0x7eea80`.

The follow-up [caller dossier](sketchup8-pushpull-caller-20261106.json), record `ev_7c01a6b044074f43c6cf61e4189733e76ae6ab84f2dc8f86a00b23608b3af3a7`, identifies `0x7f0a90` as a caller of `0x7f0670`. The latter iterates through records using virtual calls and conditionally invokes `0x7efef0`; another branch iterates and calls `0x7efda0`. This supports a conditional topology-construction path rather than simply adding the same face in every case. Fifteen call destinations are unresolved, and Ghidra marks allocator cleanup as non-returning in the pseudocode, which can distort the reconstructed control flow. Object types, branch meanings, and the full path back to the Push/Pull controller remain unproven.

A subsequent [Boolean and Push/Pull trace](SKETCHUP8-BOOLEAN-PUSHPULL-TRACE.md) connects the two tool families to a shared `CMergeController` method and identifies the solid-tool dispatcher. It does not resolve whether Push/Pull indirectly reaches the full dispatcher.
